## 2024-06-11 - React Polling Re-renders s Fetch API
**Learning:** `fetch().then(res => res.json())` vrací vždy novou referenci pole (i když jsou data identická z pohledu obsahu). Pokud tuto novou referenci bezmyšlenkovitě vložíme do React state pomocí polling intervalu (např. každých 5s), způsobíme masivní re-renderování celého stromu komponent každých 5s. Zvláště u velkých komponent jako `App.jsx` (1000+ řádků s hlubokým dom) to má razantní dopad na paměť a využití CPU i v naprostém idle režimu.
**Action:** Pro polling datových polí z API, které se nemusí změnit, je kritické před nastavením stavu provést porovnání obsahu (`JSON.stringify` nebo deep check) a v případě shody vrátit původní referenci (`return prev`).
## 2024-06-15 - Paralelizace asynchronních operací Playwrightu
**Learning:** V Playwrightu operace jako `page.goto` na různé stránky mohou blokovat jedna druhou, pokud jsou volány sekvenčně. Zvláště u operací s `networkidle` to může přidat spoustu zbytečného času navíc.
**Action:** Když nezávisle extrahujeme data z více nezávislých stránek nebo děláme screenshoty, měli bychom vždy tyto úkoly obalit do `Promise.all()`, což efektivně spustí IO asynchronní práci paralelně a zrychlí provádění celkové operace.

## 2024-05-24 - LLM Relevant Dict Filtering O(N*M) Loop
**Learning:** During text-by-text analysis for localizations in `agent.js`, constructing the `relevantDict` via `Object.keys().length` inside an `.forEach` and `.some` with repeated `toLowerCase()` on the dictionary values created unnecessary O(N*M) processing overhead. Creating array closures on every iteration of elements is very slow.
**Action:** When finding fuzzy dictionary matches for large HTML structures (DOMs), always pre-calculate the lowered string values and move processing into fast, simple nested `for` loops. Maintaining a manual counter instead of measuring object size inside inner loops avoids heavy JS engine object allocations.
## 2024-11-20 - Paralelizace Playwright CDP I/O operací na jedné stránce
**Learning:** V Playwrightu často čekáme na výsledek mnoha funkcí postupně (např. `.title()`, `.screenshot()`, `.evaluate()`). Zatímco u navigací (`.goto()`, `.click()`) záleží na pořadí, I/O operace zjišťující stav bez vizuálního dopadu na dané stránce mohou (a měly by) být prováděny paralelně pomocí `Promise.all()`. Tyto příkazy jsou odeslány do prohlížeče přes CDP naráz a prohlížeč je vyhodnotí rychleji než při čekání na round-tripy z Node.js za každým příkazem.
**Action:** Kdykoliv shromažďujeme více stavových informací nebo děláme screenshoty (které nemění vizuál), vložíme asynchronní funkce do `Promise.all()`.
## 2024-11-20 - Fast DOM traversal and getComputedStyle bottleneck
**Learning:** V Playwright `evaluate()` skriptech je volání `window.getComputedStyle` extrémně pomalá DOM operace ve srovnání s pouhým čtením vlastností jako `offsetWidth`. Její volání na tisících neviditelných uzlech nebo naivně rekurzivní procházení neviditelných DOM stromů zbytečně blokuje hlavní vlákno a zpomaluje I/O. Optimalizace pomocí pruningu na základě `offsetWidth === 0` je ovšem velmi nebezpečná pro elementy, které mají nastaveno `display: contents`, a způsobí tak nedetekování validních potomků.
**Action:** Nikdy nepoužívat jednoduché pravidlo `offsetWidth === 0` pro ignorování celých podstromů DOMu, pokud si nemůžeme být naprosto jistí strukturou CSS u dané stránky.
## 2024-11-20 - Deferred getComputedStyle optimization
**Learning:** Odložením volání funkce `window.getComputedStyle(el)` a jejím vynecháním pro prvky, které nejsou interaktivní (na základě předchozí kontroly tagů a atributů), se může procházení rozsáhlého DOMu v Playwright výrazně urychlit. Funkce `getComputedStyle` je znatelně pomalá na velkém počtu prvků a měla by být volána co nejpozději a co nejméně.
**Action:** Při zkoumání vlastností DOM elementů vždy nejdříve zkontrolujte levné atributy jako `tagName`, `getAttribute('role')` apod. a až jako poslední spoléhejte na `getComputedStyle`, pokud je to nezbytně nutné.
## 2026-06-21 - Rychlá extrakce textů z DOM (TreeWalker & Deferred getComputedStyle)
**Learning:** Procházení DOM pomocí rekurzivního volání s ohodnocováním `getComputedStyle` pro každý prvek na stránce je extrémně pomalé u složitých dokumentů, a způsobuje zbytečnou zátěž přes Playwright CDP.
**Action:** Kdykoliv potřebujeme texty, využijeme vestavěné rychlé C++ iterování přes `document.createTreeWalker` a vždy nejdříve vylučujeme vizuálně skryté uzly pomocí fast-checků geometrie (`offsetWidth === 0 || offsetHeight === 0`), a teprve pro pre-kvalifikované uzly voláme pomalé `window.getComputedStyle`.
## 2026-06-23 - Zamezení Layout Thrashingu při extrakci elementů
**Learning:** Pokud v Playwright (uvnitř `page.evaluate`) iterujeme přes mnoho DOM elementů a v rámci stejného cyklu střídáme čtení (např. `window.getComputedStyle`, `innerText`, nebo layout vlastnosti) se zápisem (např. `el.setAttribute`), způsobíme tzv. Layout Thrashing (Forced Synchronous Layout). Prohlížeč musí po každém zápisu znovu synchronně přepočítat celý layout strom před dalším čtením, což drasticky zpomaluje iteraci.
**Action:** Rozdělit procesy nad velkým množstvím elementů do dvou fází: nejprve čisté čtení (sběr všech informací a uložení cílů do pole) a následně čistý zápis v odděleném cyklu.
## 2024-11-20 - Fast iteration for DOM element collections
**Learning:** Pro obrovské kolekce DOM elementů iterované uvnitř kontextu Playwright `page.evaluate()` existuje obrovský výkonnostní rozdíl, pokud se vyhneme closure-overhead plynoucímu z nativních funkcí jako `.forEach()` na Array, a použijeme místo nich optimalizované `for` cykly s uloženou délkou pole (`const len = arr.length`). Navíc k tomu plní obrovskou roli O(1) vyhledávání v `Set` (`.has()`) oproti O(n) iterování prvků v poli pomocí `Array.includes()`, což při tisících prvků dokáže iterování uvnitř V8 zrychlit až o desítky procent (~30% pro extrakci tagů).
**Action:** Pro všechny lookup iterace iterující přes tisíce node objektů v Playwright evaluate kontextech vždy před-alokovat velikost pole, využívat klasický `for` loop a transformovat white-list arraye stringů na instance `Set`.
## 2024-11-20 - Memoizace getComputedStyle a CSS selektorů pro iterace s TreeWalkerem
**Learning:** V Playwright `evaluate()` se při auditu překladů a stránkových dillech iteruje přes všechny textové uzly v DOMu pomocí `TreeWalker` a následně se kontroluje viditelnost jejich parenta. Více textových uzlů v rámci jednoho odstavce (např. vícenásobný <b> text) způsobí opakované vyvolání `window.getComputedStyle(parent)` a zbytečné cyklické sestavování cesty přes celý řetězec DOM rodičů. Toto chování brzdí proces.
**Action:** Když iterujeme na úrovni child node (např. text node přes TreeWalker), je esenciální ukládat vypočítané meta-informace z `getComputedStyle` a stringů (jako jsou selektory) do lokální `Map()` na úrovni `parent elementu`. Při dalším textovém uzlu se shodným rodičem tak v O(1) čase převezmeme celý selektor nebo rovnou přeskočíme zbytek iterace, pokud má nastaveno `display: none`.
## 2024-11-20 - getElementsByTagName vs querySelectorAll (DOM collection perf)
**Learning:** Kdykoliv získáváme obří kolekci uzlů v Playwright `evaluate()`, volání `document.querySelectorAll('*')` trpí velkým výkonnostním penalty za to, že prohlížeč (V8 engine) musí parsovat CSS selektor a vytvářet statickou NodeList instanci. Navíc konverze těchto živých kolekcí nebo NodeList přes `Array.from()` vytváří zbytečný object a iterátor allocation overhead, který u velkých stránek s tisíci DOM prvky I/O blokuje.
**Action:** Na extrakci nebo procházení tagů využít `document.getElementsByTagName('tag')` (případně `*`), jenž funguje jako přímý lookup bez CSS parsování (vrací živou HTMLCollection téměř instantně). Pro konverzi HTMLCollection do Array uvnitř Playwright `evaluate` kontextu používat předalokované pole `new Array(len)` s primitivním O(n) `for` loopem pro optimalizaci práce s pamětí.
